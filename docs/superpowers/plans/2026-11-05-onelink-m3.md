# OneLink M3 实施计划（文件传输）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 M2.5 的聊天之上加点对点文件传输：选中会话后点 📎 选文件 → 对方收到「接受/拒绝」确认行 → 接受后流式传输并在两侧显示百分比进度 → 传完按 blake3 校验，一致才落盘到 `~/Downloads/OneLink`，不一致则失败且不留半成品。

**Architecture:** 沿用 M1/M2 的两条通道（上行 `Command` mpsc、下行 `EventQueue`），新增**第二条 ALPN** `onelink-v1-file` 专走文件数据：控制帧（offer/accept/reject）仍走 `onelink-v1` 无前缀单帧，文件字节走独立连接、全部长度前缀（`[u32 BE len][payload]`）。数据流顺序为 `FileData{xfer_id}` 头 → 若干 `[len][bytes]` 块 → `[0u32]` 结束 → `FileDone{hash}` → 等回 `FileAck`。发送/接收都由服务线程 spawn 的独立任务完成，UI 线程只收发事件。内存恒定：两侧都只用一块 `BLOCK_SIZE` 缓冲，不整文件读入。

**Tech Stack:** iroh 1.4.1（`connect(peer, FILE_ALPN)`/`accept`/`Connection::alpn()`/`open_bi`/`read_to_end`）、tokio（`fs`、`time`）、blake3 1.8（已在依赖树中，由 iroh 传递引入）、gpui-kit 0.7（`App::prompt_for_paths`）、serde_json、tracing、anyhow

**Spec:** `../../LanLink-设计方案.md`（OneLink 定稿 v0.1 2026-11-04，§5.3 文件传输）；上游计划 `2026-11-05-onelink-m2.md`

## Global Constraints

- 平台 macOS / Windows / Linux；Rust edition 2024；nightly 工具链已锁
- 控制 ALPN `onelink-v1` 与文件 ALPN `onelink-v1-file` 都不许改；端到端加密不得关闭
- 控制帧上限 `MAX_FRAME_BYTES = 64 * 1024`（`MAX_FRAMED_BYTES` 同值）；块大小 `BLOCK_SIZE = 256 * 1024`
- 接收目录固定 `~/Downloads/OneLink`（Windows 用 `%USERPROFILE%\Downloads\OneLink`），M4 设置页再做成可配
- 文件名必须清洗：只取 basename、剥控制字符、长度 ≤ 200；同名自动改名 `stem (n).ext`，**绝不覆盖已有文件**
- 传输失败/中断必须删除 `.part` 临时文件，磁盘上只允许出现完整成品
- 进度事件节流：跨过 1% 才发，且同一传输两次事件间隔 ≥ 200ms（队列容量 32，不许刷爆）
- 内存不随文件大小增长：只用固定块缓冲
- 每个任务一次 commit；`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings` 保持干净；现有 40 个测试必须保持全绿

## Review Focus

M3 的测试不覆盖、但真实使用一定会撞上的情形（每条都钉在对应任务里）：

1. **传输途中对端进程消失**：数据流 `read` 报错或返回不满 —— 双方都必须收到 `TransferFailed`，临时 `.part` 被删除，UI 不能停在 42%。
2. **恶意文件名**：对方发 `../../../../.ssh/authorized_keys`、`/etc/passwd`、带 `\0` 或 300 字符的名字 —— 落盘必须始终在接收目录内，名字被清洗成安全形式（Task 2）。
3. **同名冲突**：接收目录已有 `合同.pdf` —— 新文件必须落成 `合同 (1).pdf`，原文件字节不被改动（Task 2）。
4. **1GB 级文件**：传输过程中进程 RSS 不得随文件增长（Task 3/4 用 200MB 文件 + 块循环实现；Task 6 的 e2e 再实测速率）。
5. **进度事件刷爆队列**：1GB = 4096 块，若每块都发事件会淹没 32 容量的 `EventQueue`，导致设备上下线事件被丢 —— 必须节流；同时不能 0% 卡死不动（Task 2 的 throttle 单测 + Task 3 的实测）。
